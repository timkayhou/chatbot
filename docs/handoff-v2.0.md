# 完全本地多平台 AI 智能客服系统
## 开发交接文档 V2.0（公开版）

公开版不含具体平台和账号方案。

### 一、项目目标

开发一套完全运行于本地 Windows 的多平台 AI 智能客服系统。

系统负责自动采集客户消息、生成简单咨询回复、归纳历史聊天、建立 FAQ 知识库，以及在 AI 无法处理时转交人工。

**核心原则：稳定性优先、尽量复用成熟工具、完全本地部署、免费、自用、模块化、支持多工具同时运行。**

### 二、基本约束

#### 2.1 部署要求

- 主运行平台为 Windows。
- 所有 AI 推理在本机完成。
- 所有客户聊天记录和知识库存储在本机。
- 不部署公网服务器。
- 不依赖付费 AI API。
- 不要求独立域名或公网 IP。
- 可以在本机运行多个后台进程和本地 HTTP 服务。
- 可以使用网络下载开源软件、模型及依赖。
- 可以通过正常网络连接访问目标平台。
- 允许使用现有免费开源工具。
- macOS 暂不作为第一阶段开发目标。

#### 2.2 使用范围

软件仅由本人使用，不对外销售或分发。

因此：

- 可以接受部分维护风险较低、但尚不够成熟的开源项目。
- 可以组合多个不同语言、不同框架的工具。
- 不要求所有第三方模块统一技术栈。
- 允许保留第三方项目原始运行形式，只开发本地集成接口。
- 优先降低开发量，而不是追求统一程序或极小安装体积。

但仍应遵守适用的软件许可证及平台规则。

对于第三方组件，应明确记录技术风险，并提供关闭及人工接管机制。

### 三、Windows 主机配置

| 硬件 | 配置 |
|---|---|
| CPU | Intel Core Ultra 5 225 |
| GPU | Intel Arc Pro B60 24GB，型号待核实 |
| RAM | 48GB |
| SSD | 4TB |
| 系统 | Windows |

主要用于消息监听、AI 推理、SQLite 数据存储、历史分析和管理界面。

推荐优先测试：

- llama.cpp SYCL

### 四、平台接入要求

各平台使用原有登录状态，尽量避免频繁重新登录。

不得假设所有平台都能可靠完成无人值守自动发送。

对无法稳定自动发送的平台，允许降级为消息采集、AI 草稿与人工确认。

### 五、平台规则与发送安全

平台规则优先于自动回复。

- 发送前运行独立于 AI 模型的规则校验，不能仅依赖大语言模型的判断。
- 规则和白名单按平台配置。
- 检查联系方式、链接、图片内容、重复发送和发送频率异常。
- 图片、文件、链接、卡片消息分别记录是否支持，不能一律认为可发送。
- 不能确认是否允许发送时，按不允许处理；发送失败不反复重试。
- 不得通过拆分字符、谐音、图片或其他变形方式绕过平台规则。
- 检测到风险后拦截发送并提示人工处理。
- 不要未经确认把同名联系人自动认定为同一客户；无法确定身份关联时保持会话独立，初期可以人工绑定。
- 同一客户存在多个渠道时，避免双重自动回复。

### 六、多语言客服

系统必须支持四种语言：

1. 简体中文（zh-CN）
2. 繁体中文（zh-TW / zh-HK）
3. 日语（ja）
4. 英语（en）

#### 6.1 自动识别

根据客户消息及历史对话判断使用语言。

简体中文与繁体中文应分别处理，而不是全部转换为简体。

#### 6.2 回复语言策略

- 优先跟随客户当前语言。
- 繁体中文回复保持繁体用字。
- 日语使用适合商业客服的敬语。
- 英语使用自然、简洁的服务表达。
- 客户主动切换语言时同步切换。
- 允许在人工管理界面手动指定会话语言。

#### 6.3 知识库

FAQ 可以使用统一业务数据存储，但输出应经过语言适配。

价格、数字、单位、产品型号和 URL 不应因翻译而改变。

不同语言可以具有不同标准话术，而不是机械直译。

### 九、连接状态监控面板

**新增核心要求：所有平台必须有直观、明确、可诊断的连接状态。**

不能只显示一个绿色或红色图标。

应分别检测以下状态：

| 状态 | 含义 |
|---|---|
| 未安装 | 缺少客户端或适配组件 |
| 未启动 | 客户端或采集器没有运行 |
| 未登录 | 检测不到有效登录会话 |
| 已登录 | 已确认登录，但未验证消息读取 |
| 读取正常 | 成功读取会话或执行受支持的采集检查 |
| 发送可用 | 当前权限及界面具备发送能力 |
| 发送受限 | 平台权限、功能或风控限制 |
| 需要人工 | 需要登录、验证或处理异常 |
| 异常 | 采集器、客户端或接口故障 |

不同状态需要区分，禁止把“客户端进程正在运行”误判为“客服连接正常”。

#### 每个平台的信息卡

建议显示：

- 平台名称及账号标识。
- 当前客户端版本。
- 采集组件名称及版本。
- 登录状态。
- 最近一次成功采集时间。
- 最近一次收到消息时间。
- 最近一次成功发送时间。
- 当前读取能力。
- 当前发送能力。
- 是否启用 AI 自动回复。
- 未读消息数（可获取时）。
- 当前异常及原因。

提供操作按钮：

- 启动 / 停止。
- 重新检测。
- 打开对应客户端。
- 测试消息读取。
- 查看错误日志。
- 人工接管。

发送能力验证不能依靠未经确认的测试消息直接联系真实客户。

### 十、资源下载与快速部署

**新增核心功能：管理界面提供“资源库 / 下载中心”，用于下载、安装、升级或修复第三方工具及模型。**

目标是尽量避免手动寻找 GitHub 下载地址、配置依赖和执行复杂命令。

#### 10.1 资源分类

- 平台客户端。
- 消息采集适配器。
- Python 运行环境。
- AI 推理框架。
- AI 模型。
- OCR 依赖。
- 知识库组件。
- 其他辅助工具。

#### 10.2 下载中心功能

每个资源显示：

- 软件名称。
- 功能说明。
- 官方或项目仓库地址。
- 当前本地安装版本。
- 可下载版本。
- 许可证与使用限制。
- 下载大小（可获取时）。
- 支持操作系统。
- 安装状态。
- 是否需要额外配置。

提供按钮：

- 下载。
- 安装。
- 更新。
- 重新下载。
- 修复。
- 打开安装目录。
- 查看项目主页。

#### 10.3 一键部署要求

在技术允许时自动完成：

1. 检查系统环境。
2. 下载必要资源。
3. 校验下载文件。
4. 解压或安装。
5. 创建目录结构。
6. 安装 Python 依赖。
7. 创建本地配置。
8. 初始化数据库。
9. 检查模型文件。
10. 启动对应服务。
11. 执行健康检查。
12. 展示部署结果。

对于必须由用户登录或授权的步骤，应打开相应界面并提示人工完成。

不自动绕过验证码、安全确认或平台授权。

#### 10.4 下载安全

优先使用官方发布页面和可信仓库。

必须考虑：

- SHA256 校验。
- 安装包签名（有提供时）。
- 下载失败恢复。
- 版本兼容性。
- 依赖冲突。
- 可回滚版本。
- 避免未经审核执行任意在线脚本。

对于只有安装包、没有可审查源码的项目，应明确标记。

可以支持用户手动指定本地安装包，不强制从网络下载。

#### 10.5 离线资源缓存

4TB 硬盘允许长期缓存模型和安装资源。

建议建立：

```text
resources/
├── installers/
├── models/
├── adapters/
├── python/
├── ocr/
├── manifests/
└── cache/
```

已下载资源可以重复使用，避免每次重新部署都下载大型模型。

### 十一、AI 回复与人工接管

采用“规则优先、知识库其次、AI 生成补充”的方式。

#### 自动回复范围

- 简单问候。
- 标准服务咨询。
- 已确定的服务价格。
- 常见电脑问题。
- 维修流程说明。
- 预约方式解释。
- 设备信息收集。

#### 必须转人工

- 无法确定答案。
- 投诉和赔偿。
- 非标准报价。
- 客户要求人工。
- 需要确认真实预约空位。
- 平台规则风险。
- 平台发送限制。
- 客户身份不明确。
- 自动化工具出现异常。

人工接管后，应暂停该会话的自动发送。

#### 回复前验证

必须检查：

- 当前客户及会话是否正确。
- 是否已有更新的客户消息。
- 是否已由人工回复。
- 是否存在重复发送。
- 是否违反平台规则。
- 内容是否符合客户语言。
- 是否包含错误报价或未授权承诺。

如果无法确认发送目标，应取消自动发送。

### 十二、聊天记录和知识库自动整理

系统应能持续归纳可访问的历史聊天记录。

#### 基本流程

1. 保存消息及会话上下文。
2. 区分客户与客服消息。
3. 对消息分类。
4. 聚合相似问题。
5. 提取已有人工回复。
6. 生成标准 FAQ 候选。
7. 人工审核。
8. 加入正式知识库。
9. 后续自动调用。
10. 定期检查 FAQ 是否过期。

#### FAQ 字段

- 分类。
- 标准问题。
- 相似问法。
- 标准答案。
- 适用平台。
- 支持语言。
- 是否允许自动发送。
- 是否包含平台敏感内容。
- 来源聊天。
- 最后审核时间。
- 最后更新时间。

不同平台应支持专用回复模板及发送限制。

客户个人信息需从用于归纳的 FAQ 中删除或脱敏。

### 十四、稳定性要求

#### 14.1 多进程隔离

不同平台独立运行。

一个平台异常不能导致其他平台或 AI 服务退出。

#### 14.2 单一发送执行器

即使使用多个第三方工具，同一账号同一时刻只能由一个执行器发送消息。

避免窗口竞争、重复发送和会话错位。

#### 14.3 状态持久化

保存：

- 消息处理状态。
- 会话自动回复状态。
- 人工接管状态。
- 待发送草稿。
- 发送结果。
- 平台异常状态。

重启后能够恢复。

#### 14.4 安全降级

以下情况自动暂停发送：

- 登录状态失效。
- 客户端版本不兼容。
- 未能确认发送对象。
- 平台规则检查失败。
- 连续发送错误。
- 窗口或控件结构异常。

#### 14.5 长期运行

支持：

- Windows 登录后自动启动。
- 客户端异常检测。
- 自动恢复可安全重启的服务。
- SQLite 定期备份。
- 日志轮转。
- 资源占用监控。
- 手动重启某个适配器。

### 十六、下一轮工作要求

下一轮首先对现有工具进行技术审查，**不要直接从零开发完整系统**。

审查内容：

- 开源许可证。
- 是否完全免费。
- 是否支持当前客户端。
- 最近更新和维护情况。
- 是否容易安装。
- 是否已有可复用 API。
- 是否需要付费服务。
- 是否支持后台运行。
- 是否可能抢占其他自动化工具。
- 是否适合长时间运行。

然后设计最少自行开发代码的集成方案。

重点优先确认：

**A. 多个开源项目如何同时运行，并提供统一、准确的连接状态面板。**

**B. 如何建立一键下载、安装、校验和启动的资源管理系统。**

最终交付应包括：

- 经过核实的项目对比。
- 推荐使用的现有组件组合。
- 各平台兼容性矩阵。
- 必须自行开发的部分。
- 模块间通信方案。
- 数据库设计。
- 本地部署目录。
- 第一阶段验证程序及验收标准。

**最终目标：在不依赖云服务器和付费 AI 服务的前提下，尽可能复用成熟工具，以稳定、可维护、可人工接管的方式实现多平台本地 AI 客服。**
